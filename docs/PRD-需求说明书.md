## 1. 背景与问题

### 1.1 背景
架构设计普遍采用 **C4 模型**（Context → Container → Component → Code），它是结构清晰、层级分明的行业级表达方式。
但市面上的主流工具（Structurizr、draw.io、diagrams.net、PlantUML C4、各种白板工具）大多**偏重“画图”本身**，
对另外两件事支持很弱：

1. **把「需求」关联到架构模型** —— 无法回答“这条需求实现了哪个组件？”或“改动这个组件会影响哪些需求？”
2. **把「界面原型」关联到架构模型** —— 无法回答“这个界面属于哪个容器/组件？后端是哪个组件在支撑？”

### 1.2 存在的痛点（用户视角）
- 需求文档、架构图、原型图**三套东西各存各的**，靠人工脑补 + Excel 表格维护追溯，容易过时、断裂。
- **需求变更时**无法快速算出影响面：改一条需求，不知道牵动哪些组件、哪些界面、哪些测试点。
- 架构图与真实实现、与需求**脱节**，评审时来回翻文档，效率低、易漏。
- 个人/小团队没有重量级企业级建模平台（如 Enterprise Architect、System Architect）的预算和必要。

### 1.3 一句话定位
> **让架构师在一个本地应用里，一边画 C4 图，一边把「需求」和「界面原型」挂到架构元素上，形成可追踪、可影响分析、可版本管理的架构资产。**

## 2. 目标与成功指标

### 2.1 产品目标
1. 以 C4 四层模型为核心，提供流畅、专业的架构建模与绘图体验。
2. 建立「需求 ↔ 架构元素 ↔ 界面原型」的**双向追溯能力**，支持影响分析。
3. 用 **AI 辅助**降低建模成本：从需求/文字生成初稿、从代码仓库推断组件依赖、做一致性校验。
4. **本地优先 + git 友好**：数据以可读、可 diff 的文本格式落盘，便于备份与版本管理。
5. 面向单人或小团队，**轻量、免部署、直接安装即用**。

### 2.2 成功指标（可度量，MVP 阶段取值）
| 指标 | 目标值（MVP） |
|---|---|
| 从新建项目到产出第一张可评审的 Context 图 | ≤ 10 分钟 |
| 核心建模操作（拖拽元素、连线、缩放）无卡顿 | 10k 元素以内流畅 |
| 需求/原型挂接到架构元素的完整追溯 | 对每个核心组件可追溯 |
| 改一条需求 → 一键导出受影响清单 | 覆盖全部已挂接元素 |
| AI 生成初稿的采纳率（人工保留比例） | ≥ 60% |
| 数据可导出为 git 友好的 Structurizr DSL / JSON / Markdown | 是 |

## 3. 非目标（Non-goals）

- **不做多人实时协作**：单机/小团队，不要求多人同时编辑同一图（后期可讨论只读分享）。
- **不替代需求管理系统**：不重做 Jira/Confluence/禅道；需求来源以「应用内手动录入 + 导入 Markdown/Excel」为主，外部系统（含只读同步）列为后续可选。
- **不做完整代码级逆向工程**：AI 从代码仓库推断的是**组件/依赖级**草图，不做逐类/逐方法的完整还原。
- **不提供云端 SaaS 托管、账号体系与在线协作空间**。
- **不做白板/自由手绘**：以结构与追溯为核心，不追求无限自由画布。
- **不覆盖需求全生命周期管理**（状态流转、审批流、排期），只做“与架构/原型关联”的轻量需求档案。

## 5. 核心概念与领域模型

### 5.1 C4 模型要素
| 要素 | 说明 | 在图上的形态 |
|---|---|---|
| Person（人） | 系统的使用者/相关角色 | 人物图标 |
| Software System（软件系统） | 被描述的系统，或它依赖/交互的外部系统 | 大矩形 |
| Container（容器） | 系统内可部署/可运行的单元（如 Web 应用、数据库、消息队列） | 矩形 |
| Component（组件） | 容器内可替换/可独立设计的逻辑块 | 矩形 |
| Relationship（关系） | 元素之间的连接，带方向、说明、技术 | 带箭头连线 |
| Grouping / Boundary（边界/分组） | 把相关元素框成一组，表达上下文边界 | 虚线框/泳道 |

### 5.2 C4 视图（View）
| 视图 | 层级 | 内容 |
|---|---|---|
| Level 1 Context 上下文图 | 系统与外部 | 目标系统 + 用户 + 外部系统/依赖 |
| Level 2 Container 容器图 | 系统内部 | 系统拆成容器及其交互 |
| Level 3 Component 组件图 | 容器内部 | 某容器拆成组件及其交互 |
| Level 4 Code 代码图 | 组件内部 | 可选，组件→类（本产品可作为可选弱支持） |
| Dynamic / Deployment（可选） | 横切 | 动态交互、部署拓扑 |

### 5.3 需求（Requirement）
轻量需求档案，用于挂接到架构元素：
- 属性：编号、标题、描述、优先级、来源（手动录入 / Markdown / Excel / 后续外部系统）、状态、标签。
- 需求**本体可存在本应用内**，也可**只保留关联指针**引用外部文档（链接）。

### 5.4 界面原型（UI Prototype）
- 属性：名称、类型（截图/线框图像 / 链接）、图片路径或 URL（如 Figma）、所属容器/组件、备注。
- 支持**导入图片**与**链接 URL / Figma**（结合需求：导入图片 + 链接 URL 为主）。

### 5.5 追溯链（Traceability）
- **追溯链接（TraceLink）**：在「需求 ↔ 架构元素」和「架构元素 ↔ 界面原型」之间建立有方向的关联。
- **追溯矩阵（Traceability Matrix）**：把「需求 × 架构元素 × 原型」聚合成一张可读表格，支持正向（需求→实现）与反向（实现→需求）查看。
- **影响分析（Impact Analysis）**：给定一个变更对象（需求/元素/原型），沿追溯链自动展开受影响集合。

### 5.6 领域关系（实体简图）
```
Project（1）──<（N）Element（C4 元素：Person/System/Container/Component）
Project（1）──<（N）Relationship（元素之间的关系）
Project（1）──<（N）View（已定义的图/视图）
Project（1）──<（N）Requirement（需求）
Project（1）──<（N）Prototype（UI 原型）
Requirement（N）──<─TraceLink─>（N）Element     ← 核心追溯
Element（N）──<─TraceLink─>（N）Prototype       ← 核心追溯
Project（1）──<（N）AiSuggestion（AI 生成/校验建议）
```

## 8. 数据模型与存储格式

> 详见 `models/c4-domain.md`（本阶段先列关键约定，正式字段表后续补）。

### 8.1 实体概览
| 实体 | 关键字段 | 说明 |
|---|---|---|
| Project | id, name, description, version, created_at | 服务端项目（含成员/权限） |
| Element | id, type(Person/System/Container/Component), name, description, technology, tags, parent | 归属层级 |
| Relationship | id, source_id, target_id, type, description, technology | 有向关系 |
| View | id, type(level/context/container/component/deployment), element_ids[] | 图/视图定义 |
| Requirement | id, code, title, description, priority, status, source, tags | 需求档案 |
| Prototype | id, name, type(image/url), uri, thumbnail, notes | UI 原型 |
| TraceLink | id, from_type, from_id, to_type, to_id, link_type | 追溯链接 |
| AiSuggestion | id, type, payload, status(pending/accepted/rejected) | AI 建议区 |

### 8.2 存储设计（服务端库 + git 友好导出）
- **主存**：服务端 SQLite 库（嵌入式、零配置），承载元素/关系/视图/需求/原型/追溯链接的快速查询。
- **git 友好**：通过**导出/导入**把模型、需求、追溯关系表示为**可读文本**（Structurizr DSL / JSON / Markdown），供版本管理与外部工具消费；这些文本即是架构资产的“可 diff”形态。
- **冲突策略**：服务端为主（单机/小团队部署）；文本导出供版本管理，不做多端合并（见风险 R1）。

### 8.3 服务端文件/项目结构约定
```
archlens-server/                     # Go 后端（GoFrame），可打单二进制
├── data/                            # 运行时数据（数据库/上传）
│   ├── archlens.db                  # SQLite 主库
│   └── uploads/prototypes/          # 上传的原型图片（前端静态资源用 //go:embed 内置）
web/                                 # 前端 Vite 构建产物（嵌入二进制，由后端托管）
```

## 9. 关键交互流程

### US-S3/S4 核心追溯流程（AI + 人工）
```
1. 新建项目
2. (可选) 需求导入或录入 → 生成需求清单
3. 画 C4 图（手动 或 AI 生成初稿后人工调整，AI 只进建议区）
4. 建立追溯：选中需求 → 挂接到对应 Element；选中 Prototype → 挂接到对应 Container/Component
5. 变更一条需求 → 触发【影响分析】→ 列出受影响 Element + Prototype + 相关需求
6. 通过【追溯矩阵】确认覆盖、查看缺口 → 导出清单或 Markdown 报告
7. 提交评审（AI 校验通过）→ 版本快照 → 可 git 提交
```

### US-S6 代码仓库推断流程
```
选择本地代码目录 → AI 扫描/采样（不整体上传敏感代码，可配置范围）
→ 输出候选 Container/Component 与依赖草图（进建议区）
→ 人工确认/修正 → 写回模型
```

## 11. 验收标准（Acceptance Criteria，按核心功能）

1. **C4 建模**：能在画布拖动生成 Person/System/Container/Component，连接关系含方向与说明，切换 Context/Container/Component 视图保留对应元素。
2. **需求导入**：导入 Markdown/Excel 后，需求条目字段正确、可回滚；能录入并编辑需求。
3. **原型接入**：能导入图片、链接 URL/Figma；原型可预览并挂接到指定 Container/Component。
4. **追溯**：需求↔元素、元素↔原型可建立链接；追溯矩阵正反可查；改需求→影响分析列出**全部**受影响对象。
5. **AI 生成**：从文字/需求生成 C4 初稿，结果先入建议区，采纳后写入模型；不覆盖用户已确认内容。
6. **AI 校验**：能按命名规范/追溯缺口/层级完整性输出问题清单，并可定位到画布。
7. **存储**：项目数据持久化于服务端库；可导出为 Structurizr DSL / JSON / Markdown（git 友好）；自动保存/恢复正常。
8. **导出**：导出 Markdown 可读；导出的结构化数据可被外部工具消费。

### 13.3 技术选型（已确定方向）
- **产品形态**：Web 应用（B/S），对标 IcePanel
- **前端**：React 18 + TypeScript + Vite
- **画布/图渲染**：React Flow（@xyflow/react）自定义 C4 节点（Person/System/Container/Component、连线、自动布局、过滤）

- **数据库**：SQLite（GoFrame gdb 驱动）；可平滑迁移 PostgreSQL
- **文件/图片**：服务端磁盘目录存上传原型
- **部署**：单机/小团队自托管单二进制，一键启动
- **工程化**：pnpm + Vite + ESLint/Prettier + Vitest + Playwright；Go 用 golangci-lint + go test
